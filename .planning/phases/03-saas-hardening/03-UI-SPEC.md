# Phase 3 — SaaS Hardening: UI Design Contract

> Visual and interaction contract for Phase 3. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **Design language source: Phase 1 UI-SPEC (`.planning/phases/01-core-loop-mvp-differentiator/01-UI-SPEC.md`) + Phase 2 UI-SPEC (`.planning/phases/02-graph-collaboration-depth/02-UI-SPEC.md`). This phase EXTENDS that system — no redesign, no parallel visual system.**
>
> Scope note: billing page, plan-limit enforcement UI, onboarding flow, analytics dashboards, and the UI-relevant slice of deployment polish (environment indicator). The deployment pipeline **documentation** is non-UI and out of this contract's scope.

---

## Design System

| Property          | Value                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------- |
| Tool              | shadcn (`bun --filter @workspace/ui add <component>`)                                 |
| Preset            | shadcn v4 + Base UI (`@base-ui/react`) — style `base-nova`, base color neutral        |
| Component library | Base UI (shadcn v4 default)                                                           |
| Icon library      | lucide-react (existing)                                                               |
| Font              | Inter Variable (`@fontsource-variable/inter`, existing)                               |
| Styling           | Tailwind CSS v4 utility classes; tokens in `packages/ui/src/styles/globals.css`       |
| Dark mode         | Existing ThemeProvider (`.dark` variant) — every new component must define both modes |

**Confirmed baseline (do NOT change):** app shell layout (`app-shell.tsx`: h-14 topbar, collapsible `w-60` sidebar, `space-y-1` NavLink list with `bg-muted font-medium` active pattern), page-title convention `text-2xl font-semibold` on every authenticated route, Card primitives (`rounded-lg border`), button variants, role-badge classes from `user-menu.tsx`, org-scoped route pattern (`/orgs/:orgId/members`), data-testid anchoring pattern, existing `--chart-1..5` tokens.

## Spacing Scale

Same scale as Phase 2 (multiples of 4 only, Tailwind defaults):

| Token | Value | Usage                                                            |
| ----- | ----- | ---------------------------------------------------------------- |
| xs    | 4px   | Icon gaps, meter label gaps, table cell padding (`px-2 py-1`)    |
| sm    | 8px   | Compact element padding (`p-2`), plan-card inner gaps, chip gaps |
| md    | 16px  | Default element spacing (`gap-4`, Card padding `p-4`, form rows) |
| lg    | 24px  | Section padding, page-to-card gap (`space-y-6`), banner padding  |
| xl    | 32px  | Layout gaps, analytics grid gutter (`gap-8`), empty-state rhythm |
| 2xl   | 48px  | Major section breaks, onboarding step vertical rhythm            |
| 3xl   | 64px  | Page-level spacing — unused this phase except empty states       |

Exceptions:

- **Usage meter height** = `h-2` (8px, on-grid) — a 6px/4px bar is unnecessary; keep 8px for visibility at all fill levels.
- **Plan card min-height** = `min-h-44` (176px, on-grid) — uniform card height for the two-tier grid; not a spacing token.
- **Onboarding step container** = `max-w-md` — a max-width constraint, not a spacing value; page itself stays full-width under the app shell.
- Interactive controls keep a minimum `h-8` (32px) hit target, as in Phase 2. No 44px exception.

## Typography

Weights declared: **400 (regular)** + **600 (semibold)** only (existing `font-medium` kept where it already exists; new components use 400/600). Sizes declared: **4** (12/14/18/24px).

| Role    | Size              | Weight | Line Height | Where                                                                                                                                                           |
| ------- | ----------------- | ------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Label   | 12px (`text-xs`)  | 400    | 1.4         | Plan meta (billing cycle, limits), usage meter captions, table cells, env badge, timestamps                                                                     |
| Body    | 14px (`text-sm`)  | 400    | 1.5         | Billing descriptions, analytics stat captions, onboarding copy, empty-state body, banner body                                                                   |
| Heading | 18px (`text-lg`)  | 600    | 1.2         | Card titles (Current plan, Usage this month), section headings, empty-state headings, dialog title                                                              |
| Display | 24px (`text-2xl`) | 600    | 1.2         | Page titles on new routes — **Billing**, **Analytics**, **Get started** (matches existing `text-2xl font-semibold` convention on Dashboard/Boards/Members/Chat) |

Note: Phase 2's 20px display role (Graph view title) is **inherited unchanged** — it is not reused by new Phase 3 pages, which are full app-shell pages and follow the 24px page-title convention. No 16px size is introduced; plan card plan-name headings render at **18px/600**, with the price at **24px/600** below it (the price is the one exception to the page-title-only use of 24px — it is a numerical display, not a page title).

Rules: all copy inherits `text-foreground` / `text-muted-foreground`; no new sizes or weights beyond the four declared.

## Color

Same tokens as Phase 1/2 — **no new semantic tokens this phase.**

| Role            | Token                                                                     | Usage                                                                                                                                                                                                |
| --------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dominant (60%)  | `--background` (light `oklch(1 0 0)` / dark `oklch(0.145 0 0)`)           | Page background behind billing, onboarding, analytics                                                                                                                                                |
| Secondary (30%) | `--card`, `--muted`, `--secondary`                                        | Plan cards (bg-card), current-plan highlight (bg-muted), stat cards (bg-card), usage meter track (bg-muted), sidebar/nav (existing)                                                                  |
| Accent (10%)    | `--primary` (neutral: light `oklch(0.205 0 0)` / dark `oklch(0.922 0 0)`) | **Reserved for:** page-title-free CTAs ("Upgrade to Pro", "Choose Pro", "Get started", "Create board"), active nav item, selected plan card border, focus rings, links, usage-meter fill under limit |
| Destructive     | `--destructive` (existing red)                                            | **Destructive actions only this phase:** "Cancel subscription", "Downgrade to Free" confirm buttons, and exceeded usage-meter fill / limit text                                                      |

**Accent reserved for (explicit list):** primary CTA buttons (upgrade/choose/get-started), active sidebar NavLink (`bg-muted font-medium` — existing), selected plan card border (`ring-2 ring-primary`), focus rings, inline links, and usage-meter fill when under limit. **Never used for decorative fills, charts, or background washes.**

**Usage meter fill contract (concrete):** fill uses `--primary` below 80% of limit; at ≥80% fill switches to `--chart-1` (amber, existing token — a warning, not accent); at 100% (limit reached) fill and the "x / y" value text switch to `--destructive`. This is **data encoding of limit state**, not a new token.

**Chart colors (data encoding — NOT part of the 60/30/10 budget):** analytics SVG bars reuse the existing `--chart-1..5` tokens as a fixed mapping per metric: `--chart-1` cards created, `--chart-2` proposals approved, `--chart-3` comments posted, `--chart-4` members active. Same mapping in light and dark (tokens already have `.dark` overrides in `globals.css`).

**Env indicator:** staging badge = `bg-amber-500/15 text-amber-600` pill (uses existing amber-500 hue from the edge-dependency token family); **production renders no badge at all** (hidden, not muted). Not a new semantic token — a fixed environment convention.

## Views & Interactions

### V1. Sidebar navigation additions (extends `app-shell.tsx`)

- Add two org-scoped NavLinks after "Members", rendered only when `selectedOrgId` is set (same pattern as Members):
  - **Billing** → `/orgs/:orgId/billing` (`CreditCard` lucide icon optional)
  - **Analytics** → `/orgs/:orgId/analytics` (`BarChart3` lucide icon optional)
- Active state: existing `bg-muted font-medium` NavLink pattern. `data-testid`: `nav-billing`, `nav-analytics`.

### V2. Billing page (`/orgs/:orgId/billing`, route `billing.tsx`)

Page title "Billing" (`text-2xl font-semibold`), `space-y-6` layout. Data from `useBilling(orgId)` → `GET /api/orgs/:orgId/billing` returning:

```
BillingState = {
  plan: "free" | "pro",
  cycle: "monthly",                      // fixed this phase
  price: { free: 0, pro: 12 },           // USD/mo, display-only
  limits: { projects, members, aiActions, cards },
  usage:  { projects, members, aiActions, cards },
  checkoutUrl: string | null,            // per-tier checkout (hosted Stripe)
  portalUrl: string | null               // Customer Portal
}
```

**V2a. Current plan card** (`data-testid="current-plan"`):

- `Card` with header "Current plan" (18px/600); body: plan name ("Free" / "Pro") at 14px/600 + cycle caption "Billed monthly" (12px muted).
- Right side actions: `billing-manage` (outline, sm, `ExternalLink` icon, "Manage billing") linking to `portalUrl` when `plan === "pro"`; when `plan === "free"` this button is hidden and the upsell lives in V2b.
- Loading: 2 skeleton rows (`animate-pulse bg-muted rounded-md h-4`).

**V2b. Plan selection grid** (`plan-cards.tsx`, `data-testid="plan-grid"`):

- Two plan cards side by side (`grid gap-4 md:grid-cols-2`), each `Card min-h-44 flex flex-col p-4`:
  - **Free** (`data-testid="plan-card-free"`): plan name "Free" (18px/600), price "$0 /mo" (24px/600) with "/mo" at 12px muted, 3 limit rows (12px, `Check` icon 12px): "2 projects · 5 members · 50 AI actions/mo · 500 cards" — concise single-line-per-limit list.
  - **Pro** (`data-testid="plan-card-pro"`): "Pro", "$12 /mo", limit rows: "Unlimited projects · 25 members · 5,000 AI actions/mo · Unlimited cards".
- **Selection interaction:** the card for the **current** plan shows a disabled `current-plan-badge` ("Current plan", 12px, `bg-muted text-muted-foreground`); the other card shows a primary CTA:
  - On Free, Pro card CTA: **"Upgrade to Pro"** (`data-testid="plan-select-pro"`) → `POST /api/orgs/:orgId/billing/checkout { tier: "pro" }` → redirect to returned `checkoutUrl` (hosted Stripe Checkout). Button shows "Redirecting…" while pending.
  - On Pro, Free card CTA: **"Downgrade to Free"** (`data-testid="plan-select-free"`, outline/destructive-tinted variant) → opens `plan-change-dialog` (V2d).
- Selected/current emphasis uses `ring-2 ring-primary` on the current plan card (accent contract: selection only).

**V2c. Usage meters** (`usage-meters.tsx`, `data-testid="usage-section"`):

- `Card` "Usage this month" (18px/600). One meter per limit metric (Projects, Members, AI actions, Cards), stacked `space-y-4`:
  - Row: metric label (14px/600) + value "x / y" (12px muted, `data-testid="usage-value-{metric}"`) on the same line.
  - Bar: `h-2 rounded-full bg-muted` track, fill = `rounded-full` div with `style={{ width: pct }}` (`data-testid="usage-bar-{metric}"`, `data-pct` attr). Fill color per meter-fill contract (primary < 80%, chart-1 ≥ 80%, destructive at 100%).
  - AI actions row carries a "resets monthly" caption (12px muted).
- At ≥80%: inline warning caption next to value — "{metric} nearly exhausted — upgrade for more headroom." (12px, `text-chart-1`-equivalent amber: use `text-amber-600`/dark `text-amber-500`... **use `text-chart-1` via `text-chart-1` token** — token compiles to amber, matches fill).
  - At 100%: caption "Limit reached — upgrade to Pro to continue." (12px, destructive).
- `data-testid`: `usage-meter-{metric}` per meter wrapper, `usage-value-{metric}`, `usage-bar-{metric}`.

**V2d. Plan-change confirmation dialog** (`plan-change-dialog.tsx`, shadcn `Dialog`):

- Triggers: "Downgrade to Free" (V2b). `data-testid="plan-change-dialog"`.
- Title: "Downgrade to Free?" (18px/600). Body (14px/400): "You'll lose Pro features at the end of the billing cycle. If you're over a Free-plan limit, extra projects, members, and cards are kept but locked until you upgrade or reduce usage."
- Buttons: ghost "Keep Pro" (`data-testid="plan-change-cancel"`, 14px) + destructive "Downgrade to Free" (`data-testid="plan-change-confirm"`).
- Confirm → `POST /api/orgs/:orgId/billing/downgrade` (or portal-backed) → success toast "You're now on the Free plan." → invalidate `useBilling`. Failure toast "Couldn't update your plan. Try again." (destructive-tinted).
- **Cancel subscription is out of UI scope this phase** (only downgrade Free↔Pro, both tiers selectable per success criterion 1).

**V2e. Error state:** banner in page — "Couldn't load billing info." + `Retry` button (`data-testid="billing-retry"`, refetches). 402/403 limit errors from any mutation surface the `limit-banner` (V4) instead of a plain error toast.

### V3. Onboarding flow (`/onboarding`, route `onboarding.tsx`)

**Trigger:** first-run detection — after auth, a user with **zero projects across all their orgs** is redirected to `/onboarding` (via `ProtectedRoute` guard or dashboard redirect; exact mechanism per planner). "Skip" dismisses for the session (no re-redirect loop). Existing projects → never redirected.

**Layout:** single page under app shell (topbar visible, sidebar as usual). `max-w-md mx-auto` centered column, `space-y-8`, `py-12`. Step indicator: 2 steps, 12px muted ("1 of 2") — no progress bar (short flow).

**Step 1 — Welcome** (`data-testid="onboarding-welcome"`):

- Heading (24px/600): "Welcome to Storyteller" — or, if the user has orgs but no projects, "Welcome to {org name}".
- Body (14px/400): "Turn a product idea into a living requirements board — AI generates, reviews, and keeps your stories in sync." (reuses Phase 1 value prop).
- CTA: primary "Get started" (`data-testid="onboarding-start"`) → Step 2.

**Step 2 — Choose a starting point** (`data-testid="onboarding-template"`):

- Heading (24px/600): "How would you like to start?" Body: "Pick a template or begin with a blank board." (14px).
- Template cards (`template-card.tsx`): horizontal list / 2-col grid of `Card` options, each with icon (lucide, 14px), name (14px/600), one-line description (12px muted), and a "Use template" primary sm button (`data-testid="onboarding-template-{templateId}"`):
  - **Blank board** (`template-blank`): "Blank board" — "Start from scratch with an empty board." → creates empty project via existing `POST /api/projects` (navigates to `/projects/:slug`).
  - **Sample: Product launch** (`template-product-launch`): "Sample — Product launch" — "A sample requirements board seeded with example epics and stories." → `POST /api/orgs/:orgId/projects/template { templateId: "product-launch" }` → navigates to the seeded board.
  - (Additional templates optional — one blank + one sample is the contract minimum.)
- Secondary: "Skip for now" ghost link (`data-testid="onboarding-skip"`, 14px) → navigates to `/projects`. No re-trigger this session.

**Step 2 empty/error state:** template creation failure → inline error under the cards "Couldn't create your board. Try again." (12px destructive) + the buttons re-enable.

### V4. Plan-limit enforcement (hard-block — user-confirmed)

Server enforces limits (API returns 402/403); UI reflects and pre-empts. **Contract: hard-block with tooltip + banner + upsell.**

**V4a. Disabled action tooltips** — any action that would exceed a plan limit is disabled with a tooltip "Limit reached — upgrade to Pro" (`data-testid="limit-tooltip"`). Concretely:

| Action                             | Limit metric        | Existing surface                                   |
| ---------------------------------- | ------------------- | -------------------------------------------------- |
| "New board" (topbar + Boards page) | projects            | `app-shell.tsx`, `projects.tsx`                    |
| "Invite" (Members page)            | members             | `org-members.tsx`                                  |
| Chat generate / "Ask AI" (send)    | aiActions (monthly) | `project-chat.tsx` (disable submit when exhausted) |
| Card creation via AI approval      | cards               | enforced server-side; UI shows `limit-banner`      |

Disabled = `disabled` attribute (not hidden) so the tooltip can anchor; disabled button style follows existing `button.tsx` disabled variant.

**V4b. Global limit banner** (`limit-banner.tsx`, mounted in `app-shell.tsx` above `<Outlet />`):

- Rendered when `useBilling(orgId).usage[metric] >= limits[metric]` for any metric (from `GET /api/orgs/:orgId/billing`, shared by V2).
- Look: `bg-muted/50 border-b` full-width strip, `px-4 py-2` flex row gap-3, 14px body: "You've reached your {plan} {metric} limit." (metric label lowercased, e.g. "project", "member", "AI action") + primary sm CTA **"Upgrade to Pro"** (`data-testid="limit-banner-upgrade"`) → navigates to `/orgs/:orgId/billing`.
- `data-testid="limit-banner"` + `data-limit-metric` attr. Dismissible? **No** — persistent while over limit (hard-block must stay visible); hiding is not allowed.
- If `usage` is not yet available (loading), render nothing (no flash).

**V4c. Server-rejected mutation:** if a mutation still 402s (race / non-client-known limit), show the `limit-banner` (invalidate billing) and a destructive toast "Limit reached — upgrade to Pro to continue."

### V5. Analytics dashboard (`/orgs/:orgId/analytics`, route `analytics.tsx`)

Org-level usage analytics (SAAS-02), 30-day default range. Data from `useAnalytics(orgId)` → `GET /api/orgs/:orgId/analytics?range=30d`:

```
AnalyticsState = {
  totals: { cardsCreated, proposalsApproved, commentsPosted, activeMembers },
  series: { cardsCreated: [{ date, value }], proposalsApproved: [...], commentsPosted: [...] },
  generatedAt: string
}
```

**V5a. Stat cards row** (`stat-card.tsx`): `grid gap-4 sm:grid-cols-2 lg:grid-cols-4` of `Card p-4` — value (24px/600), label (12px muted) ("Cards created", "Proposals approved", "Comments posted", "Active members"). Each `data-testid="analytics-stat-{metric}"` (`analytics-stat-cardsCreated` etc.).

**V5b. Trend charts** (`bar-chart.tsx`, custom SVG — user-confirmed, no recharts):

- One chart per series, `Card p-4`: title (14px/600) + "Last 30 days" caption (12px muted).
- SVG bar chart: `viewBox` fixed (e.g. 560×160), bars `rect` per series point, `fill` = fixed metric color from the chart-color mapping, `rx=2` rounded caps. Bar width computed from series length; gap between bars ≥ 2px. No axes/ticks — value tooltip only (Phase 3 keeps charts simple; native `title` element per bar = `title="{date}: {value}"`).
- Empty series (all-zero): empty state (V5c).
- `data-testid`: `analytics-chart-{metric}` on the svg, `analytics-bar-{metric}-{index}` per rect, `data-value` attr per bar.
- A11y: each `rect` gets `<title>`; charts are decorative-duplicated by the stat cards, so `aria-hidden="true"` on the svg + the stat cards carry the accessible value.

**V5c. Empty state** (no activity in range): centered stack `py-24` — heading "No activity yet" (18px/600), body "Generate your first story cards, approve a proposal, or post a comment — your team's usage stats will appear here." (14px/400), CTA "Open Chat" (`data-testid="analytics-empty-cta"`, navigates to `/projects`).

**V5d. Error state:** banner — "Couldn't load analytics." + `Retry` (`data-testid="analytics-retry"`).

### V6. Environment indicator (deployment polish, UI slice)

- `env-indicator.tsx` mounted in `app-shell.tsx` topbar, right side before the user menu.
- Reads `import.meta.env.VITE_APP_ENV ?? import.meta.env.MODE`:
  - `staging` → pill "Staging" (12px, `bg-amber-500/15 text-amber-600`, `data-testid="env-badge"`, `data-env="staging"`).
  - anything else (production/local `development`) → **render nothing** (no pill in dev, no pill in prod).
- Non-UI deployment pipeline documentation (CI config, env vars, rollout) is out of this contract.

## API Contract (consumed by UI)

| Endpoint                                                       | Purpose                                 | Notes                                                                       |
| -------------------------------------------------------------- | --------------------------------------- | --------------------------------------------------------------------------- |
| `GET /api/orgs/:orgId/billing`                                 | Plan + limits + usage + checkout/portal | Shape per `BillingState` in V2; server is source of truth for prices/limits |
| `POST /api/orgs/:orgId/billing/checkout` `{ tier }`            | Create hosted Stripe Checkout           | Returns `{ url }` → full-page redirect; no Stripe.js in bundle              |
| `POST /api/orgs/:orgId/billing/downgrade`                      | Downgrade to Free                       | Confirmation handled in UI dialog; returns updated `BillingState`           |
| `GET /api/orgs/:orgId/billing/portal`                          | Customer Portal URL (invoices/payment)  | Or returned inline in `billing` payload (`portalUrl`)                       |
| `GET /api/orgs/:orgId/analytics?range=30d`                     | Totals + daily series                   | Shape per `AnalyticsState` in V5                                            |
| `POST /api/orgs/:orgId/projects/template` `{ templateId }`     | Create project seeded from sample       | Seeds epics+cards (product-launch); returns `{ slug }`                      |
| Limit-blocked mutations (projects, invites, AI actions, cards) | 402/403 with structured body            | UI maps to `limit-banner` + toast; must not render as generic error         |

## Interaction & Feedback Rules

- All mutations (upgrade checkout, downgrade, template create) show pending button state ("Redirecting…", disabled) and inline/toast errors — no silent failures.
- Limit state is **server-truth**: UI meters/banner reflect `GET /api/orgs/:orgId/billing`; a 402/403 on any mutation invalidates billing and surfaces `limit-banner` — never a generic error.
- The `limit-banner` is non-dismissible while over limit; hiding it would hide the hard-block rationale.
- Loading states: billing page shows skeleton rows; analytics shows skeleton stat cards (`animate-pulse bg-muted rounded-lg h-20` ×4) + skeleton chart block; onboarding templates show 2 skeleton cards. No full-page spinners.
- Charts are static renderings of fetched data — no client-side animation, no refetch on window focus (30d data is stable within a session).
- Toasts (existing pattern) reserved for: plan change success/failure, limit-blocked mutation, export-style transient failures.
