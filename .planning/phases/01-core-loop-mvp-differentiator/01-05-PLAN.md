    services/apply-proposal.ts — the approval transaction (APPR-01/02/03, DATA-02/06, VEC-03):
    - `applyProposal({ proposalId, approverId }: { proposalId: string; approverId: string }): Promise<{ applied: number }>` — inside db.transaction:
      1. Load proposal with status — if not "pending" → throw 409 "Proposal already resolved".
      2. Load its proposal_changes (ordered by createdAt).
      3. For each change (create/update/close):
         - create: insert card { id: uuid, projectId, title, description, acceptanceCriteria, status, priority, epicId (resolve epicName → epic row, create epic if missing), customFields, slug: unique slugify(title) with `-2`/`-3` suffix on collision within the project }; insert card_version { cardId, versionNo: 1, ...snapshot of all fields, changeType: "create", createdBy: approverId, sourceProposalChangeId }; insert card_relation rows from change.relationSummary (dependency/hierarchy/evolution — source/target resolved); insert card_attachment rows for any attachmentFileIds in change.newData.
         - update: load target card — if missing → skip + log; **if card.isClosed → throw 409 "Cannot update closed card" (closed-card immutability bypass blocked — T-05-02; the engine already converted these, this is the backstop)**; apply fields from change.fields (never is_closed/closed_by/closed_at); insert card_version { versionNo: max(existing)+1, changeType: "update", ... }; insert relations from relationSummary.
         - close: load target card — if missing → skip; set isClosed=true, closedBy=approverId, closedAt=now (idempotent if already closed — log + skip version); insert card_version { versionNo: max+1, changeType: "close" }.
      4. Update proposal { status: "approved", approvedBy: approverId, approvedAt: now }.
      5. After each create/update/close version insert, call reindexCard({ cardId, provider: aiProvider, versionId }) — VEC-03; wrap failures in try/catch + log (embedding failures must not roll back the approval — but keep the rest transactional). Closed cards get their embedding replaced (persists).
      6. Return { applied: changesApplied }.
    All writes through the Drizzle query builder (no raw SQL). Logger: createLogger("api").
  </action>

## Trust Boundaries

| Boundary                         | Description                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| client → AI/proposal/card routes | Untrusted bodies + project ids cross here — validateBody + resolveOrgFromProject gate |
| approval action → DB             | The apply transaction mutates many tables — atomicity is the integrity gate           |
| card ids → closed-card state     | Attacker-supplied target ids could target closed cards                                |

## STRIDE Threat Register

| Threat ID | Category               | Component                                      | Disposition | Mitigation Plan                                                                                                                                                                                                 |
| --------- | ---------------------- | ---------------------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-05-01   | Information disclosure | proposal/card ids                              | mitigate    | resolveOrgFromProject scopes every route; a project id from another org fails membership (403) before any row is read — cross-tenant reads blocked (HIGH)                                                       |
| T-05-02   | Tampering              | applyProposal update/close                     | mitigate    | Closed-card immutability enforced at apply time: any update on isClosed=true throws 409 inside the transaction (rolls back); the engine guard (plan 01-02) already converts these — this is the backstop (HIGH) |
| T-05-03   | Elevation              | approve/reject                                 | mitigate    | requireRole("owner","admin","member") on approve/reject — viewer (read-only) can never resolve a proposal; role resolved from the membership row per request, not from client input                             |
| T-05-04   | Tampering              | proposal re-approval / double-apply            | mitigate    | applyProposal loads status inside the transaction and throws 409 on non-pending; status check + writes are in one transaction so no TOCTOU double-apply                                                         |
| T-05-05   | Injection              | newData / relationSummary / conflictFlags JSON | mitigate    | Values originate from the plan 01-02 strict schemas (engine output) or plan 01-01 Zod validations (manual paths); applyProposal never trusts raw body fields — it reads typed change records                    |
| T-05-06   | Denial of service      | /api/ai/\* abuse                               | mitigate    | rateLimiter(10, 60_000) mounted on /api/ai/\* reusing the existing in-memory limiter with setInterval cleanup                                                                                                   |
| T-05-07   | Tampering              | manual update smuggling is_closed              | mitigate    | updateCardSchema is .strict() (plan 01-01) and rejects is_closed/closed_by/closed_at keys; plus the service-level closed-card 409                                                                               |
| T-05-SC   | Tampering              | npm installs                                   | accept      | No new npm dependencies in this plan                                                                                                                                                                            |

</threat_model>
